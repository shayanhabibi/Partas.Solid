# Partas.Solid.Tests.Runtime

Runtime tests for Partas.Solid. The snapshot tests in `Partas.Solid.Tests.Plugin` pin the JSX the plugin
emits. These tests run that JSX and check what it does:

1. **Fable + the Partas plugin** compile F# fixtures to `*.fs.jsx`. The flags match the snapshot tests
   (`--exclude Partas.Solid.FablePlugin --noCache -e .fs.jsx -c Release --optimize`), plus `-o .`.
2. **The real Solid 2 JSX compiler** (`@solidjs/vite-plugin` → `@solidjs/compiler`, pinned to
   `2.0.0-rc.9`) turns that JSX into DOM code inside vitest.
3. **vitest + jsdom** run specs that mount components and assert on the actual DOM and reactive behaviour.
   `solid-js` / `@solidjs/web` `2.0.0-rc.9` resolve to their **browser development** builds.
   `helpers/setup.js` fails every run that picks up the server or production build.

## What is covered

| Suite / folder | What it exercises |
| --- | --- |
| `Primitives/Reactivity` | signals (value/updater writes, `equals`), memos (laziness, diamonds, dependency switching, `MemoOptions`), effects (two-phase, cleanup, error bundles, render/tracked effects), ownership (`createRoot`, `onCleanup`, `onSettled`, `untrack`, `getOwner`/`runWithOwner`, `getObserver`, context defaults), `mapArray`/`repeat` |
| `Primitives/StoresAsync` | `createStore` and setters, `reconcile`, derived stores / `createProjection`, async memos, actions, `createOptimistic`/`createOptimisticStore`, store utils (`omit`, `snapshot`, `merge`) |
| `Dom/Elements` | tag structure and text children, attributes (class/style/bool/data/aria/`.attr`), delegated and native events, refs, SVG, spreads, `@solidjs/web` (`Portal`, `Dynamic`) |
| `Integration/Components` | props (getters, `merge` defaults, rest spreads), context, control flow (`Show`/`For`/`Switch`/`Match`/`Errored`/`Loading`), reactive re-rendering and lifecycle, abstract component composition, component-body tracking semantics |
| `Integration/Apps` | small realistic apps: todo list, signup form with validation, disclosure/tabs, sidebar with context, sortable data table, async search with `Loading`/`Errored`/`isPending` |
| `*/Smoke` | one minimal case per suite that proves the pipeline works |

Tests marked `it.fails` are **known Partas.Solid bugs**. Each one carries a `// BUG:` comment next to it.
List them all with `grep -rn "BUG:" Primitives Dom Integration`. When a bug is fixed, the `it.fails` test
starts passing, which vitest reports as a failure. Change it to a plain `it` then.

## Layout

```
Partas.Solid.Tests.Runtime/
  package.json, package-lock.json   exact pins: solid-js, @solidjs/web, @solidjs/compiler, @solidjs/babel-plugin 2.0.0-rc.9
  vitest.config.mjs                 one config for all suites (jsdom, solid plugin over **/*.jsx, browser+development)
  run.mjs                           compile (with a cross-process lock) and then run vitest
  helpers/index.js                  mount, withRoot, flush, act, click, input, settle, waitFor, deferred, text
  helpers/setup.js                  vitest setupFile: auto-cleanup, checks for the browser/dev build
  Primitives/                       suite: reactive primitives, no DOM (createSignal, createMemo, effects, stores...)
  Dom/                              suite: DOM elements/attributes/tags rendered by components
  Integration/                      suite: DOM elements and primitives together (events, control flow, async)
    Partas.Solid.Tests.Runtime.<Suite>.fsproj   net9.0, compiles every **/*.fs under the suite
    <CaseFolder>/Foo.fs             F# fixture
    <CaseFolder>/Foo.fs.jsx         generated by Fable (gitignored)
    <CaseFolder>/Foo.test.js        vitest spec importing ./Foo.fs.jsx
    Partas.Solid/, fable_modules/   generated by Fable per suite (gitignored, reserved names)
```

Each suite is its own Fable project and compiles on its own.

## Running

Requires Node >= 22.12 and the .NET SDK. `run.mjs` runs `dotnet tool restore`, and runs `npm ci` if
`node_modules` is missing.

```sh
cd Partas.Solid.Tests.Runtime
node run.mjs all                        # compile all three suites, run every spec
node run.mjs dom                        # compile Dom only, run Dom specs only
node run.mjs integration -t "counter"   # extra args go to vitest (here: filter by test name)
node run.mjs primitives MyCase          # vitest file filter: only paths containing "MyCase"
node run.mjs dom --no-compile           # skip Fable, rerun specs against the existing .fs.jsx
npm test | npm run test:primitives | npm run test:dom | npm run test:integration
```

A Fable compile takes about 10 s per suite. When only a `.test.js` changed, use `--no-compile`.

The build CLI runs this suite after the Expecto plugin tests:
`dotnet run --project partas-solid.fsproj -- test` runs `npm ci` and then `node run.mjs all`.
With `--quick`, an existing `node_modules` is reused. `--skip-tests` skips this stage along with the
other test stages.

### Concurrency

Several processes can run `run.mjs` at the same time. Every suite references the shared `Partas.Solid`
and `Partas.Solid.FablePlugin` projects, and parallel dotnet builds of those collide. So the **compile
step is serialised** through an atomic `mkdir` of `.compile-lock/`:

- `owner.json` holds the pid, host and a heartbeat that is rewritten every 5 s.
- Other processes print `waiting for compile lock held by pid ...` and retry.
- A lock counts as stale when its pid is dead (same host) or its heartbeat is older than 120 s
  (`PARTAS_RUNTIME_LOCK_STALE_MS`). A stale lock is removed automatically.
- Waiters give up after 30 min (`PARTAS_RUNTIME_LOCK_TIMEOUT_MS`).
- To clear the lock by hand, delete `.compile-lock/`, but only when no `run.mjs` is running.

vitest runs are not locked. One caveat: a compile of suite X rewrites X's `*.fs.jsx`. A vitest run of X
that happens during that compile can read half-written files. Runs of other suites are unaffected,
because the `-o .` output keeps each suite's generated library code inside the suite folder.

## Adding a test

1. **Pick the suite.** Use `Primitives` when no DOM is involved, `Dom` for rendering and attributes, and
   `Integration` for DOM plus reactivity (events, signals driving the DOM, control flow, async).
2. **Create your own subfolder**, e.g. `Dom/ClassAttributes/`. Do not edit other people's folders. Do not
   use the names `Partas.Solid`, `fable_modules`, `bin`, `obj` or `node_modules`.
3. **Write the F# fixture** `Dom/ClassAttributes/ClassAttributes.fs`:
   - Give it a unique module name: `module Partas.Solid.Tests.Runtime.Dom.ClassAttributes`.
     All fixtures in a suite form one F# project, so module names must be unique.
   - Every `.fs` file in the suite is compiled, in path order. When a folder has several files and
     one depends on another, prefix them (`A-Types.fs`, `B-View.fs`).
   - Components: `[<SolidComponent>] let Foo () = div (...) { ... }` compiles to `export function Foo()`.
     `[<Erase>] type Foo() = inherit div() ... [<SolidTypeComponent>] member props.View = ...` compiles to
     `export function Foo(props)`. Props are `[<Erase>] member val x: T = unbox null with get, set`.
   - Primitives: export plain functions that build signals and memos and return them in a record or
     tuple. Wrap owned computations in `createRoot (fun (dispose: unit -> unit) -> ...)` and return
     `dispose`, or call them from `withRoot(...)` in the spec.
   - A compile error in any file fails the whole suite's compile, including everyone else's specs.
     Always compile before you finish (`node run.mjs <suite>`).
4. **Write the spec** `Dom/ClassAttributes/ClassAttributes.test.js`. Specs are plain JS, and JSX is
   allowed in `.test.jsx`:

   ```js
   import { describe, it, expect } from "vitest";
   import { mount, click, flush, text } from "../../helpers/index.js";
   import { Foo } from "./ClassAttributes.fs.jsx";

   it("renders", () => {
     const { container } = mount(Foo, { someProp: 1 });
     expect(container.querySelector("div.x")).not.toBeNull();
   });
   ```
5. **Run** `node run.mjs dom ClassAttributes`. To read the generated JSX when something looks wrong,
   open `Foo.fs.jsx`.
6. **Found a Partas bug?** Keep the correct assertion, then mark the test as an expected failure:

   ```js
   // BUG: <one line describing the wrong output/behaviour>
   it.fails("does X", () => { ... });
   ```

   Do not weaken the assertion. If the plugin output does not compile at all, keep the fixture out of the
   suite (a compile error breaks every spec in it) and report the bug instead.

## Helpers (`helpers/index.js`)

| Helper | Purpose |
| --- | --- |
| `mount(Component, props?)` | Renders `Component` into a fresh `<div>` in `document.body` through `@solidjs/web` `render` + `createComponent`. Returns `{ container, root, dispose }`. The DOM is ready when it returns, because `render` flushes. Auto-disposed after each test. `mount(() => <jsx/>, undefined, { thunk: true })` renders a thunk. |
| `withRoot(fn)` | Runs `fn(dispose)` inside `createRoot` and returns `{ value, dispose }`. Auto-disposed. |
| `flush()` / `flush(fn)` | Re-exported from `solid-js`. Drains Solid's queue synchronously. `flush(fn)` runs `fn` and then drains. |
| `act(fn)` | Alias for `flush(fn)`. |
| `click(el)` / `input(el, value)` | Dispatches a bubbling DOM event (Solid delegates events to the document) and flushes. |
| `settle(rounds = 3)` | `await`s macrotask turns, flushing after each. Use after resolving a promise that feeds an async memo or `<Loading>`. |
| `waitFor(pred, { timeout })` | Polls `pred` with a flush between polls, and returns its truthy value. Throws on timeout. |
| `deferred()` | `{ promise, resolve, reject }`, to drive async resolution deterministically. |
| `text(el)` | `textContent` with whitespace collapsed. |

### How Solid 2 (rc.9) schedules updates

This is why the helpers look the way they do. See `solid/packages/signals/src/core/scheduler.ts`:
`schedule()`, `flush()`.

- A setter call **does not update anything synchronously** downstream. It marks the graph and queues
  one microtask that runs `flush()`. After `setX(1)`, the DOM and effects are stale until a flush.
  Reading a memo directly (`memo()`) does pull the fresh value.
- `flush()` drains synchronously. In tests, call `flush()` after writes, or use `click`/`input`/`act`.
  Calling `flush()` inside an effect callback is a no-op. Inside an action it throws.
- `render()` flushes once before it returns.
- Async memos (`createMemo` returning a promise) and `<Loading>` update after the promise settles and
  a later flush. Use `await settle()` or `await waitFor(...)`.
- An uncaught error in a reactive computation **halts** the reactive system. `render()` resets that in
  dev, so the next `mount()` starts clean.

## Notes

- The fsproj files are also in `Partas.Solid.slnx` under `/Tests/`, so the IDE type-checks fixtures.
  `dotnet build` of them is only a type-check. Fable produces the JS.
- The vite plugin is `@solidjs/vite-plugin@3.0.0-next.44`. Its default backend is the native
  `@solidjs/compiler`. `package.json` `overrides` pin the compiler and babel plugin to `2.0.0-rc.9`. To
  compare against the Babel backend, set `compiler: "babel"` in the plugin options in `vitest.config.mjs`.
